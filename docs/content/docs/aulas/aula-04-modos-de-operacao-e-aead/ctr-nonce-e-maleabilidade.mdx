## A única regra: contador sem repetição

Repetir um bloco de contador sob a mesma chave é repetir o fluxo de chave. **É o mesmo erro de usar duas vezes um One-Time Pad.**

<Tabs items={['Dentro da mensagem', 'Entre mensagens', 'Nonce aleatório']}>
  <Tab value="Dentro da mensagem">
    O contador cresce de 1 em 1. Com contador de 32 bits: até `2^32` blocos, 64 GiB por mensagem.
  </Tab>
  <Tab value="Entre mensagens">
    O nonce muda. Um contador de mensagens garante unicidade enquanto o estado não for perdido.
  </Tab>
  <Tab value="Nonce aleatório">
    Funciona, mas colisões ficam prováveis perto de `2^48` mensagens com 96 bits (paradoxo do aniversário). Exige limite de uso por chave.
  </Tab>
</Tabs>

## Reuso de nonce: o XOR entrega tudo

Se dois textos são cifrados com o mesmo fluxo de chave:

```
C1 XOR C2 = (P1 XOR S) XOR (P2 XOR S) = P1 XOR P2
```

A chave de fluxo some e sobra o XOR dos textos claros, com a redundância da língua. Se uma das mensagens é conhecida (ou parcialmente previsível, como um cabeçalho), a outra sai: `P2 = C1 XOR C2 XOR P1`. O mesmo vale para imagens: o XOR de dois ciphertexts com o mesmo nonce revela o contorno de ambas.

## Maleabilidade: o CTR não protege contra alteração

Um XOR no texto cifrado vira o **mesmo XOR** no texto claro.

| | Conteúdo |
|---|----------|
| Texto claro | `PAGAR R$ 0100,00 A JOAO` |
| Alteração Δ no byte 9 | `'0' XOR '9' = 30 XOR 39 = 09` |
| Decifrado pelo destinatário | `PAGAR R$ 9100,00 A JOAO` |

O CTR é CPA seguro e, mesmo assim, **totalmente maleável**: o atacante não aprendeu nada sobre o texto, mas o alterou de forma previsível. Confidencialidade e integridade são garantias diferentes.

<Callout title="Aplicação no artigo" type="warn">
  É a mesma limitação do One-Time Pad (Aula 2, limite 3). Ela motiva a próxima seção: os modos de confidencialidade, sozinhos, não bastam, e o TLS 1.3 usa apenas cifração **autenticada**.
</Callout>
